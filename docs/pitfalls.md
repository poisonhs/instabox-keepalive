# 踩坑记录

按踩到的顺序排列。每条都是实际撞过的，不是推测。

## 1. 用符号表推断保活机制，方向错了

`strings` 看到 `activity.go`、`ActivityProbes`、`probe output has no "busy"`，就认定平台在检测 CPU busy，于是写了每分钟烧 3 秒 CPU 的心跳。

**结果**：心跳每分钟准点执行，一次没缺席，机器照样被冻结 941 秒。

**教训**：二进制里的符号只说明"有这么个功能"，不说明"这个功能决定暂停"。必须用行为验证——停掉一切操作，观察多久被冻；加上某个措施，再观察。控制变量，别靠推断。

## 2. 连平台自己的 agent 都被冻

发现 guest agent 每 5 分钟的 `op=reclaim` 在同一时间窗也断档。

这一条直接排除了"应用层判定"的可能：如果平台能在应用层感知活跃度，它自己的 agent 不该被冻住。

## 3. `timeout` 的退出码导致脚本跑两遍

```sh
# 错误写法
nice -n 19 chrt --idle 0 timeout 3 yes > /dev/null 2>&1 || timeout 3 yes > /dev/null 2>&1
```

看起来是"chrt 不可用时兜底"，实际 `timeout` 超时的退出码是 **124（非零）**，所以第一条执行完必然触发第二条，3 秒变 6 秒。

**正确写法**——用能力探测代替 `||`：

```sh
if chrt --idle 0 true 2>/dev/null; then
  nice -n 19 chrt --idle 0 timeout 3 yes > /dev/null 2>&1
else
  timeout 3 yes > /dev/null 2>&1
fi
```

## 4. 日志轮转把脚本搞挂了

```sh
tail -n 200 "$LOG" > /tmp/x && mv /tmp/x "$LOG"
```

在 systemd oneshot 环境里偶发 `mv: cannot stat`，加上 `set -e` 直接让脚本中途退出。

而且这个轮转根本没必要——每分钟一次也就 1440 行/天。直接 `>>` 追加。

## 5. 15 秒一次触发网关限流

长连接脚本一开始设 15 秒一次，第 2 次请求就收到：

```
13:08:48 CONNECTED
13:08:48 200 36B
13:09:03 429 41B   ← Too Many Requests
13:09:19 200 36B
```

改成 60 秒后稳定。**网关有速率保护，太密的请求反而像攻击。**

## 6. 把 429 当成故障

一开始看到 `429` 和 `000` 以为沙盒挂了。实际上：

| 码 | 指向 |
|---|---|
| `429` | 本地节奏太快，网关限流 |
| `000` | DNS / 网络超时 |
| `502` | **沙盒内该端口没服务** |

只有 `502` 才说明沙盒侧有问题。全程 521 次请求里 0 次 `502`，证明沙盒一次没停。

## 7. 用同名产品文档指导实施

搜 `instabox` 找到的是瑞典一家快递柜公司，完全无关。GitHub 上的 `InsForge/InsForge` issue 讲的是 project 暂停，也不是这个沙盒。

**教训**：以机器里 `strings` 出现的包路径为准（`github.com/<org>/<product>`），不要拿同名项目的文档当本产品文档。

## 8. 沙盒重启后服务消失

`/etc/systemd/system/` 里的单元文件在重启后没了——文件系统回滚到快照。

**处理**：装好服务后，用平台的快照功能存一次。没有快照功能就只能每次重启后重跑安装脚本。

## 9. 半开连接要等超时窗口

从暂停恢复后，旧的 SSH 隧道连接处于半开状态，sshd 要等满 `ServerAliveInterval × ServerAliveCountMax` 才判定死亡并重连。

恢复后一两分钟内隧道没回来是正常的，**先等够这个窗口再排查**，别急着重建。
